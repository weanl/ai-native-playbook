# M2-024 UI 技术选型评估

## 结论

M2-029 建议采用“重构 Streamlit 工作台”的阶段性方案，不在 M2 直接引入 React / Next.js 前端工程。

推荐路径：

```text
M2-024：完成产品设计与静态 HTML 原型
M2-029：基于设计重构 Streamlit 工作台
M2+ / M3：若触发迁移条件，再启动独立 frontend engineering proposal
```

原因：

- M2 的主风险在持续学习、数据版本、模型 artifact、模型注册和晋级生命周期，而不是前端工程化。
- 当前项目已有 Streamlit demo 基线，M2-029 可在较低工程成本下验证工作台信息架构。
- 直接迁移前端会引入路由、构建、部署、API 边界、状态管理等额外复杂度，容易挤压 M2 核心闭环。

## 候选方案

### 方案 A：继续使用现有 Streamlit 页面结构

含义：

- 在现有 `src/nextaiops_algo/ui/app.py` 上继续追加页面和控件。

优点：

- 成本最低。
- 与现有 demo 连续。

缺点：

- 单文件膨胀风险高。
- 难以承载持续学习、模型版本、history 和 evidence panel 的复杂信息架构。
- 状态和组件复用弱。

结论：

- 不推荐作为 M2-029 方案。

### 方案 B：重构 Streamlit 工作台

含义：

- 仍使用 Streamlit，但按 M2-024 页面规格组织页面、组件和状态。
- 将页面、状态展示、表格、evidence panel、history detail 等拆分为清晰模块。

优点：

- 保持 M2 工程复杂度可控。
- 能快速验证产品主线。
- 适合本地 demo 和客户评审。
- 不需要新增前端依赖。

缺点：

- 复杂交互、精细布局和状态管理仍受 Streamlit 约束。
- 长任务实时刷新和多对象同步体验有限。
- 后续权限、审计、多用户协作会遇到边界。

结论：

- 推荐作为 M2-029 默认方案。

### 方案 C：迁移到 React / Next.js 等正式前端

含义：

- 新增独立前端工程，通过 API 与后端交互。

优点：

- 路由、组件复用、状态管理、复杂表格、审计流和权限扩展更自然。
- 更接近正式产品形态。

缺点：

- M2 需要额外定义 API 边界。
- 引入构建、部署、测试和依赖管理。
- 会扩大 M2 范围，推迟持续学习闭环验证。

结论：

- 不建议在 M2-029 直接启动；可作为 M2+ / M3 独立 proposal。

## Rubric

评分：分数越高，表示该方案越适合 M2 当前目标。对成本类维度使用正向命名，例如“离线 demo 简单度”“部署简单度”和“M2 交付可控性”。

| 维度 | 现有 Streamlit 追加 | 重构 Streamlit | React / Next.js |
|---|---:|---:|---:|
| 多页面信息架构 | 2 | 4 | 5 |
| 长任务状态刷新 | 2 | 3 | 5 |
| Plotly / 大表格交互 | 3 | 3 | 5 |
| 状态管理 | 1 | 3 | 5 |
| 组件复用 | 1 | 3 | 5 |
| 离线 demo 简单度 | 5 | 5 | 3 |
| 部署简单度 | 5 | 4 | 2 |
| 未来认证 / 权限 / 审计扩展 | 1 | 2 | 5 |
| M2 交付可控性 | 5 | 4 | 1 |
| M3 可演进性 | 1 | 3 | 5 |

解释：

- 现有 Streamlit 追加虽然成本最低，但会继续积累 UI 结构债务。
- 重构 Streamlit 在 M2 交付可控性和产品验证之间平衡最好。
- React / Next.js 最适合正式产品，但应建立在 API 和生命周期模型稳定之后。

## M2-029 建议边界

M2-029 如果采用重构 Streamlit，应做：

- 按 M2-024 信息架构组织页面。
- 引入明确页面模块和组件模块。
- 展示 Data、Experiments、Batch Compare、Strategy Simulation、Continuous Learning、Models、History 的核心闭环，其中 Strategy Simulation 是 M2 的一级模块，而不是 Continuous Learning 的附属说明。
- 优先支持多数据集实验矩阵、批量比较、离线策略模拟报告和效果指标。
- 使用 evidence panel 支撑 candidate promotion 叙事。
- 保留静态或 mock fallback，便于 demo。

M2-029 不应做：

- 不新增独立前端工程。
- 不引入认证 / 权限。
- 不实现多租户。
- 不实现无人值守真实 auto-active。
- 不为了策略模拟自动修改真实 active pointer。
- 不为了 UI 重构修改 core 契约。
- 不在没有 proposal 的情况下修改 SQLite schema。

## 接受的妥协

在 M2 中继续使用 Streamlit，需要接受：

- 复杂交互不追求正式 SaaS 产品级体验。
- 长任务刷新可以用手动刷新或轻量轮询表达，不追求实时协作。
- 复杂表格可以先保留基础筛选和排序，不追求完整数据网格。
- 策略模拟可先以离线批处理结果、指标表和 active timeline 呈现，不追求实时调度编排。
- 视觉精度以信息清晰为主，不追求像素级还原静态 HTML 原型。

## 迁移触发条件

满足以下任一条件，应启动独立前端迁移 proposal：

- 需要多用户、权限、审批流或审计角色。
- 需要复杂路由、深链接和跨页面状态保持。
- 需要大量可复用组件和复杂表格交互。
- 需要实时任务状态、通知中心或多人协作。
- Streamlit 页面拆分后仍无法承载 Models / History / evidence panel 的核心体验。
- 客户演示从内部 prototype 转向正式产品试用。

## 风险

主要风险：

- 重构 Streamlit 仍可能被框架布局能力限制。
- 如果 M2-025 到 M2-028 的后端对象命名变化较大，M2-029 需要调整页面映射。
- 过早追求视觉精细度会拖慢持续学习闭环。

缓解方式：

- M2-029 以 M2-024 文档为产品锚点，以后端 proposal 为数据锚点。
- 保持 UI 文案与对象状态清晰可替换。
- 将 frontend migration 明确留给 M2+ / M3 proposal。
