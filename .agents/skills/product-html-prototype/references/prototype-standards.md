# Prototype Standards

A good prototype must communicate product behavior, not only visual layout.

## Minimum quality bar

Every generated prototype should include:
- clear product name or page context
- primary user goal
- clear navigation or page structure
- realistic sample data
- primary call to action
- secondary actions
- useful empty states
- useful error states
- useful success feedback
- responsive layout
- clear visual hierarchy

## Product thinking checklist

Before generating UI, infer:
- Who is the user?
- What is the user trying to accomplish?
- What is the fastest path to success?
- What information does the user need first?
- What can be hidden until later?
- What states can break the happy path?
- What action should be most visually prominent?

## HTML constraints

Default to:
- one HTML file
- embedded CSS
- embedded JavaScript
- no external dependency
- no framework
- no build step
- no remote asset

## Fidelity

Create a high-fidelity prototype when enough detail exists.
Create a medium-fidelity prototype when the document is vague.
Avoid raw low-fidelity wireframes unless explicitly requested.

## Content

Use realistic placeholder data.
Avoid lorem ipsum.
Use product-specific examples inferred from the document.
